# Miguel / OCEAN Handoff — Controlled Evolution Mockup v0.6.1

## Purpose

This document explains how to review the OCEAN / iOceans controlled evolution mockup without confusing it with a finished product, a production system or a real-data integration.

The mockup is a controlled operational prototype. Its purpose is to make the system obvious before connecting real data, real users, real infrastructure or real APIs.

## Current release

Current release: v0.6.1

Main branch and develop branch are synchronized at the same release commit.

## What to show first

Start with the system idea:

- This is not a dashboard decoration exercise.
- This is not a generic AI demo.
- This is not a finished platform.
- This is a controlled operating model for evidence, states, review gates, audit references and governed AI actions.

Then show the screens in this order:

1. Budget
2. Opportunities
3. Governed AI
4. Evidence
5. Logs

This order makes the business and operational flow easier to understand.

Do not claim that this mockup:

- Uses real OCEAN data
- Uses real iOceans credentials
- Connects to real APIs
- Contains real scientific measurements

- Performs real AI calls
- Produces scientific conclusions
- Automates commercial outreach
- Replaces executive decisions
- Replaces human approval
- Is a production-ready platform

## What to say to Miguel

Suggested wording:

This mockup is deliberately controlled. The goal is not to impress with decoration, but to make the system structure visible: what enters, what state it has, who reviews it, what AI can and cannot do, what evidence exists, what logs are generated and where human approval is required.

The important part is that every visible area is backed by synthetic fixtures and validated by checks. There is no real OCEAN data, no real API connection and no hidden production dependency.

## What to say to OCEAN

Suggested wording:

This is an early operational model for a future OCEAN / iOceans system. It shows how budget, opportunities, scientific evidence, audit logs and governed AI actions could be represented in one controlled interface.

The mockup is not trying to be the final product. It is designed to make the operating model understandable before real integration work begins.

## Demo guardrails

During review, keep these guardrails explicit:

- Synthetic data only
- No production dependencies
- No credentials
- No real scientific data
- No real customer data
- No external API calls
- No autonomous AI action
- No commercial action without review
- No scientific claim without validation
- No executive action without decision gate

## Internal strategic framing

Engineering clarity criterion:

Make the system obvious. Every module should explain the entity, state, input, output, permission, review gate and audit trace.

Execution discipline criterion:

Ship controlled increments. Keep release discipline, use branches, tags, validation gates and small visible progress.
